# Android app

Sudo Sapient for Android is a [Trusted Web Activity](https://developer.chrome.com/docs/android/trusted-web-activity)
(TWA): a small Android app that opens the web app full screen in Chrome (or another browser that
supports TWAs), with its own icon, name, splash screen and notifications. The app _is_ the website,
so every change to the site reaches it at once. A new APK is only needed when the shell changes:
name, icon, colours, shortcuts, notification settings, or a new Bubblewrap version.

It is not on Google Play. We build a signed APK ourselves and install it directly ("sideload").

The project is generated by [Bubblewrap](https://github.com/GoogleChromeLabs/bubblewrap) 1.27.0 from
`twa-manifest.json`, and uses android-browser-helper 2.7.4.

| File                                                    | What it is                                                                                                                                |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `twa-manifest.json`                                     | The settings: package id, host, colours, icons, shortcuts, version. Edit this, never the generated files.                                 |
| `generate.js`                                           | Regenerates the project from `twa-manifest.json` (`node apps/android/generate.js`).                                                       |
| `build.sh`                                              | Builds, signs and checks a release APK.                                                                                                   |
| `create-keystore.sh`                                    | Creates the signing key, once.                                                                                                            |
| `app/`, `gradle/`, `build.gradle`, `settings.gradle`, … | The generated Gradle project, committed so a release builds without Bubblewrap and a change to it shows in review. Don't edit it by hand. |
| `out/`                                                  | Build output: APKs, logs, work copies. Git-ignored.                                                                                       |

## Choices

- **Package id `dev.sudosapient.app`, name "Sudo Sapient", host production.** `startUrl` is `/`,
  the same as the web manifest's `start_url`.
- **Display `standalone`, orientation `default`.** The web manifest sets no orientation and the app
  works in both, so the app follows the phone's rotation setting, and tablets can use landscape.
- **Colours.** The status bar, navigation bar and splash screen use the page background, `--bg` in
  `src/styles/tokens.css`: `#fbfaf8` in light mode and `#1a1a19` in dark mode (the same pair as
  `theme-color` in `index.html`), so nothing flashes a different colour as the page loads. The
  navigation bar divider is set to the bar's own colour, so there's no visible line. (Bubblewrap
  writes a transparent divider as black.) Bubblewrap has only one splash colour, so `generate.js`
  adds a dark-mode one (`res/values-night/colors.xml`, from `themeColorDark`). Android picks the
  light or dark set from the phone's setting. A theme chosen in the app's own settings doesn't
  change the bars (see Known limits).
- **Icons**, all from `public/icons/` in this checkout:
  - launcher: `icon-512.png` for Android 7.0–7.1, and `icon-maskable-512.png` as the adaptive icon
    on Android 8+ (the wordmark stays inside circle and squircle masks);
  - splash: `icon-512.png`;
  - notifications: `icon-monochrome-512.png`. Bubblewrap 1.27.0 uses `monochromeIconUrl` only for
    the notification small icon (`ic_notification_icon`), whose safe area is the middle 20 of 24 dp.
    That's what the icon was drawn for (80% of the square). Bubblewrap doesn't make an Android 13+
    themed icon (the adaptive icon has no `<monochrome>` layer), so there is nothing to clip and no
    padded variant is needed. With themed icons on, the launcher shows the normal icon.
- **Shortcuts**: Inbox (`/#inbox`) and My Tasks (`/#mytasks`) on a long press of the icon, as in the
  web manifest, with the same app icon. Android adds a third, "Site settings" (`enableSiteSettingsShortcut`),
  where people can manage notifications and clear the site's data.
- **Notifications**: `enableNotifications` turns on notification delegation. Chrome hands the
  site's Web Push notifications to the app, which shows them under its own name and icon, not
  Chrome's. On Android 13+ the app declares `POST_NOTIFICATIONS`; when the page asks for permission,
  Chrome asks the app and the app shows Android's permission prompt
  (`NotificationPermissionRequestActivity` in android-browser-helper).
- **Links**: an `autoVerify` intent filter claims every `https://<host>/` link, so a link such as
  `/#task/WEB-12` in an email or Slack opens in the app. The whole link, `#…` included, is passed to
  the page. A production build claims only production. A staging build claims only staging.
- **Fallback `customtabs`.** If the site can't be verified, or the default browser can't run a TWA,
  the app opens the site in a Custom Tab (a browser tab with a small address bar), which still has
  the person's browser session, push notifications and file uploads. The `webview` fallback would
  need the `INTERNET` permission and has none of those.
- **SDK levels.** `minSdkVersion` is 24 (Android 7.0): android-browser-helper 2.7.4 requires it,
  and Bubblewrap's default of 21 doesn't build. Target and compile SDK are 36 (Android 16): Bubblewrap's
  setting and the newest platform. Google Play raises its required target each August (35 from
  2025), but Play's rules don't apply to a sideloaded app. The APK is signed with v2 and v3 signatures. v1 is only for Android 6 and older.
- **Version**: `appVersionCode` 1, `appVersion` (the version name) `1.0.0`. They are the Android
  shell's own version, separate from the web app's.
- **Off**: Play Billing, location delegation, ChromeOS-only, Meta Quest and alpha dependencies are
  all off. The app has no use for them. There is no `webManifestUrl`: it only serves ChromeOS and
  Meta Quest, and it would make every regeneration download the live manifest.
- **Asset links.** The server builds `/.well-known/assetlinks.json` from `ANDROID_PACKAGE_NAME` and
  `ANDROID_CERT_FINGERPRINTS`. `fingerprints` in `twa-manifest.json` stays empty, and no static
  assetlinks file is made or needed. `signingKey` is left out too: `build.sh` signs, not Bubblewrap.

## Prerequisites

- JDK 17 in `JAVA_HOME`, and an Android SDK in `ANDROID_HOME` with platform `android-36` and
  build-tools (36.0.0 or later; `build.sh` uses the newest one installed). Gradle and its plugins
  download on the first build.
- Node.js and pnpm (the repository's own), only to regenerate the project or make a test build.
  `generate.js` runs Bubblewrap with `pnpm dlx`, so nothing is added to the root `package.json`.

What is pinned: Bubblewrap's version (1.27.0, not its own dependencies) and the Gradle download
(`distributionSha256Sum`, added by `generate.js`). The Android Gradle plugin and libraries come from
Google's Maven and the `jcenter()` that Bubblewrap's template still lists (read-only, kept because the
generated files aren't edited by hand), without a verification file. So a build today is the same as
one tomorrow on this machine, but a regeneration or a new machine can fetch different dependencies:
compare the version and fingerprint `build.sh` prints before handing an APK out.

## Signing key

Every APK must be signed with the same key: Android only installs an update signed like the
installed app. **If the key or its password is lost, the app can never be updated.** People would
have to uninstall it and install a new app. **Anyone who has both can ship an update as us.** So:

1. Put the password in a file outside the repository, readable only by you (first line only):

   ```sh
   mkdir -m 700 -p ~/.sudo-sapient-keys
   (umask 077 && openssl rand -base64 33 > ~/.sudo-sapient-keys/android-release.pass)
   ```

2. Create the key (RSA 4096, valid 10000 days, alias `sudo-sapient`). The script refuses to replace
   an existing keystore or write inside the repository, and prints the certificate fingerprint:

   ```sh
   JAVA_HOME=<jdk17> apps/android/create-keystore.sh \
     --keystore ~/.sudo-sapient-keys/android-release.jks \
     --pass-file ~/.sudo-sapient-keys/android-release.pass
   ```

   It runs `keytool -genkeypair` (PKCS12, RSA 4096) with `-storepass:file` and `-keypass:file`, so
   the password never appears on a command line.

3. **Back up** the `.jks` file and the password in two places that aren't this machine, such as a
   password manager (the password, and the keystore as an attachment) and an encrypted drive. Never
   commit them, send them in chat or attach them to an issue. `.gitignore` refuses `*.jks`,
   `*.keystore`, `*.p12`, `*.pass` and APKs as a second guard.

## Build

```sh
export JAVA_HOME=<jdk17> ANDROID_HOME=<android-sdk>
export ANDROID_KEYSTORE=~/.sudo-sapient-keys/android-release.jks
export ANDROID_KEYSTORE_PASS_FILE=~/.sudo-sapient-keys/android-release.pass

apps/android/build.sh             # production
apps/android/build.sh --staging   # staging
apps/android/build.sh --host my-test.example.com   # any other HTTPS host
```

Each option has a flag as well (`--keystore`, `--keystore-pass-file`, `--alias`, default
`sudo-sapient`, and `--key-pass-file` for a key password that differs from the keystore's). The
script stops with a message if one is missing, or if the keystore or a password file is inside the
repository. Passwords are only read by `apksigner` from their files. They never appear on a
command line, in Gradle properties or in the logs.

A production build compiles the committed project as it is. It warns if `apps/android` or
`public/icons` has uncommitted changes, since a release should come from a commit. It then:

1. copies the project to `out/work/<target>/` and runs `./gradlew --no-daemon assembleRelease`
   (log: `out/gradle-<target>.log`; no Gradle daemon is left running);
2. aligns the APK (`zipalign -p 4`), signs it with `apksigner` (v2 and v3), and runs
   `apksigner verify --verbose --print-certs` (saved next to the APK as `.verify.txt`);
3. prints the APK's path, package id, version, host and certificate fingerprint, and the two
   variables to set on the deployment.

Output: `out/sudo-sapient-<version>-<code>.apk`, or `out/sudo-sapient-staging-…` and
`out/sudo-sapient-test-…`.

### Test builds

`--staging` or `--host` builds an app for another origin without editing committed files. The
script regenerates its copy of the project with Bubblewrap (`generate.js --out`), so it needs
Node.js, pnpm and a network connection the first time. A test build is a different app:

| Target      | Package id                    | Name                     | Opens                                          |
| ----------- | ----------------------------- | ------------------------ | ---------------------------------------------- |
| production  | `dev.sudosapient.app`         | "Sudo Sapient"           | https://sudo-tracker-production.up.railway.app |
| `--staging` | `dev.sudosapient.app.staging` | "Sudo Sapient (staging)" | https://sudo-tracker-staging.up.railway.app    |
| `--host`    | `dev.sudosapient.app.test`    | "Sudo Sapient (test)"    | that host                                      |

So it installs next to the real app, can't be mistaken for it, and can never replace it. Because
each deployment serves one package name, the staging deployment's `ANDROID_PACKAGE_NAME` is
`dev.sudosapient.app.staging`. `--package-id` and `--name` change the test identity. Signing a test
build with the release key is fine, since the package id differs. A separate test key also works,
as long as its fingerprint is the one set on that deployment.

## Set up the deployment

`build.sh` ends with, for example:

```
For https://sudo-tracker-production.up.railway.app/.well-known/assetlinks.json, set on that deployment:
  ANDROID_PACKAGE_NAME=dev.sudosapient.app
  ANDROID_CERT_FINGERPRINTS=AB:CD:…
```

Set those two variables on the Railway service of that environment and redeploy (see
[deployment](../../docs/deployment.md#the-android-app) and
[configuration](../../docs/configuration.md#android-app)). The fingerprint is public, not a secret.
It's the same for every APK signed with that key, so this is needed once per environment, not per
release. `keytool -list -v -keystore <keystore> -alias sudo-sapient -storepass:file <pass file>`
prints it too (the `SHA256:` line).

## Install

- **With a cable**: turn on USB debugging (Settings → About phone → tap "Build number" seven times,
  then Settings → System → Developer options → USB debugging), connect, and run
  `adb install -r apps/android/out/sudo-sapient-1.0.0-1.apk`.
- **Without**: copy the APK to the phone (download, Drive, …), open it in Files, and allow "Install
  unknown apps" for that app when asked. Play Protect may warn about an unknown developer. Choose to
  install anyway.

The phone needs Chrome, or another browser that supports Trusted Web Activities. The first launch
needs a connection.

## Check that it's verified

When verification works, the app opens with no address bar. If a small address bar shows the
site's address at the top, Chrome couldn't confirm that the site trusts this app, and fell back to a
Custom Tab. Check, in order:

1. The file: `curl -si https://<host>/.well-known/assetlinks.json` answers `200`, with
   `Content-Type: application/json`, no redirect, and the APK's package name and fingerprint. A `404`
   means a variable isn't set on that deployment. Google's checker gives the same answer Android
   gets:
   `curl 'https://digitalassetlinks.googleapis.com/v1/statements:list?source.web.site=https://<host>&relation=delegate_permission/common.handle_all_urls'`.
2. The fingerprint is the one `build.sh` printed for this APK
   (`apksigner verify --print-certs <apk>`, or the `.verify.txt` next to it).
3. Android's view (Android 12+): `adb shell pm get-app-links dev.sudosapient.app` should list the
   host as `verified`. To check again after fixing the file:
   `adb shell pm verify-app-links --re-verify dev.sudosapient.app`. Android and Chrome cache the
   result, so after a change reinstall the app or clear its data and Chrome's.
4. Logs: `adb logcat | grep -iE 'TWA|OriginVerifier|DigitalAssetLinks'` while opening the app.

## Ship an update

Only when the shell changes (see the top of this page). Updates to the site need no APK.

1. In `twa-manifest.json`, raise `appVersionCode` by one (Android refuses a lower code than the installed
   one, and an equal one is a reinstall of the same version, so every APK you hand out needs its own) and set `appVersion`, e.g. `1.1.0`.
2. `node apps/android/generate.js`, then commit `twa-manifest.json` and the regenerated project.
3. `apps/android/build.sh` with **the same key**, and install the new APK over the old one
   (`adb install -r`, or open it on the phone). Data and sign-in are kept.

## Regenerate the project

After changing `twa-manifest.json`, the icons in `public/icons/` it names, or the Bubblewrap version
in `generate.js`:

```sh
node apps/android/generate.js
git diff --stat apps/android   # review what changed, then commit it
```

`generate.js` serves this checkout's `public/` on 127.0.0.1 and points Bubblewrap at it, so the app
gets the icons of the commit it's built from, even before they're deployed. The URLs in
`twa-manifest.json` say where those files are published, and only their path is used. Bubblewrap
gets a temporary config, so it doesn't prompt and doesn't touch `~/.bubblewrap`. Running it twice
gives the same files. Changes to `public/manifest.webmanifest` don't reach the app on their own:
copy what applies (name, colours, shortcuts) into `twa-manifest.json`.

## Known limits

- Needs Chrome (or another TWA-capable browser) on the phone. Without one, the app opens the site
  in whatever browser there is.
- The status bar follows the theme picked in the app's settings (the page's `theme-color`). The
  navigation bar follows only the phone's light or dark setting (`navigationColor` and
  `navigationColorDark`, fixed when the app starts Chrome): a page can't change it, so with the app
  on the other theme it keeps the phone's colour.
- The first launch needs a connection. After that, the service worker opens the app shell offline.
- No themed (monochrome) launcher icon on Android 13+, since Bubblewrap doesn't generate one.
- Google has announced developer verification for apps installed outside Play on certified Android
  devices, rolling out by country from 2026. Where it applies, sideloading this app may need a
  registered developer or `adb install`.
